Internal Developer Platform · self-hosted

De git push à la production,
sans une commande kubectl.

Guide de déploiement complet d'une plateforme développeur souveraine, 100% GitOps, sur un cluster Kubernetes auto-hébergé. Reprenez-le depuis zéro sur un nouveau cluster : chaque phase construit une brique, avec les commandes, les choix d'architecture et les pièges déjà rencontrés.

Développeur ──push──▶ Gitea ──webhook──▶ Tekton ──build/push──▶ Harbor │ └──bump──▶ <app>-config ──▶ Argo CD ──▶ Production (TLS) Backstage ── "Create" ──▶ scaffolder ──▶ 2 repos Gitea ──▶ (la boucle ci-dessus) Vault ──▶ External Secrets ──▶ Secrets K8s (tous les composants)
Point de départ

Prérequis du cluster

Ce guide part d'un cluster Kubernetes nu et le transforme en IDP complète. Voici le socle supposé en place avant la Phase 0.

ÉlémentValeur de référence
HyperviseurProxmox VE
Clusterkubeadm — 1 master + 2 workers, Kubernetes v1.33
OS des nœudsRHEL 10 (ou équivalent)
CNICalico
Domaine*.apps.itssolutions.me → 10.10.0.240
DNSCloudflare (accès API pour le solver DNS-01)
StockageUn disque dédié par worker pour Longhorn
⚠ Leçon matérielle capitale

Le disque qui porte etcd (sur le master) conditionne la santé de TOUT le cluster. Un disque lent (HDD, ou bus IDE émulé, ou stockage partagé saturé) provoque des etcdserver: request timed out qui se propagent en cascade : API server qui rate des réponses → Longhorn qui ne réconcilie plus → volumes dégradés, bases qui redémarrent. Prévoyez un SSD/NVMe dédié au master, sur bus VirtIO SCSI. Voir la section « La saga du disque ».

Phase 0

Fondations déployé

Rendre le cluster capable d'exposer des services avec IP et TLS valides.

  1. MetalLB — IPAddressPool 10.10.0.240-250 + L2Advertisement (mode L2, pas de BGP).
  2. ingress-nginx — Service LoadBalancer (10.10.0.240), avec le flag --default-ssl-certificate=ingress-nginx/wildcard-apps-tls : un seul certificat wildcard sert tout *.apps, aucun secret TLS à répliquer par namespace.
  3. cert-manager — ClusterIssuer staging + prod, solver DNS-01 Cloudflare. Certificate wildcard *.apps.itssolutions.me.
  4. Longhorn — 2 réplicas, disques dédiés sur les workers (scheduling désactivé sur le disque OS).
  5. DNS Cloudflare — enregistrements en nuage GRIS (DNS only ; le proxy orange ne joint pas les IP privées).
  6. sysctl — inotify instances/watches et file-max relevés sur tous les nœuds (leur épuisement corrompait des PVC).
Piège résolu — split-DNS

Des résolutions divergentes interne/externe causaient des erreurs TLS intermittentes. Solution : une seule source de vérité DNS (Cloudflare, nuage gris).

Phase 1

GitOps · Argo CD déployé

Tout l'état du cluster décrit dans Git, réconcilié automatiquement.

  1. Installer Argo CD (server.insecure: true derrière nginx qui termine le TLS).
  2. Pattern app-of-apps — bootstrap/root-app.yaml (appliqué une seule fois à la main) pointe platform-repo/apps/. Tout fichier ajouté est déployé, ordonné par sync-waves (0 → 13).
  3. Règle de vie du projet : toute modification passe par commit + push.
# accélérer la prise en compte d'un changement
kubectl -n argocd annotate application <x> argocd.argoproj.io/refresh=hard --overwrite
Phase 2

Secrets · Vault + External Secrets déployé

Aucun secret en clair dans Git ; une source unique.

  1. Vault standalone Raft (PVC Longhorn, namespace vault-itssolutions), init + unseal scriptés. Clés de unseal sauvegardées hors cluster (perte = réinitialisation).
  2. External Secrets Operator + ClusterSecretStore vault (auth Kubernetes, policy de lecture secret/data/*).
  3. Pattern uniforme pour tout le projet : le secret dans Vault → un ExternalSecret dans le namespace consommateur → un Secret K8s synchronisé.

Wrapper de session Vault

# vault-0 perd sa session à chaque restart ET revient TOUJOURS sealed
read -s VROOT   # root token (saisie masquée)
vput() { kubectl -n vault-itssolutions exec -i vault-0 -- sh -c "VAULT_TOKEN='$VROOT' vault $*"; }
Réflexe n°1 du projet

ESO InvalidProviderConfig / secrets qui ne synchronisent plus → vault status → unseal. C'est le premier geste à tenter devant la moitié des incidents.

Phase 3

Registre & CI · Harbor + Tekton déployé

Builder et stocker les images en interne.

  1. Harbor — PVCs Longhorn, admin via ExternalSecret. Projet apps privé. Robot robot$apps+ci (push+pull) → token dans Vault.
  2. Tekton vendoré (pipelines, triggers, interceptors — app Argo dédiée, ServerSideApply).
  3. Pipeline générique build-and-promote — trois tâches enchaînées :
    • git-clone-lite : fetch + checkout FETCH_HEAD (robuste au lost+found d'un PVC non vide), le commit court = tag image
    • kaniko-build : dockerconfig monté sous le nom config.json
    • gitops-bump : yq du tag dans le values.yaml du repo <app>-config
⚠ Deux pièges qui coûtent des heures

Simples quotes obligatoires pour tout secret contenant $ (le $ de robot$apps — les doubles quotes le mangent).

Harbor UNAUTHORIZED malgré des credentials valides → kaniko ne lit que config.json, jamais .dockerconfigjson. Monter le secret dockerconfig sous le nom config.json (ExternalSecret de type Opaque).

Phase 3.5

Forge · Gitea + ApplicationSet déployé

Héberger le code en interne, et découvrir automatiquement les applications à déployer.

  1. Gitea — chart officiel, SQLite + cache memory + queues level (tous les sous-charts Bitnami désactivés : images retirées de Docker Hub).
  2. Organisation itssolutions + comptes de service : tekton-ci, argocd (PAT avec read:issue — sinon 403 obscurs), backstage.
  3. Webhook d'organisation → EventListener Tekton, interceptor github (Gitea émet des headers GitHub-compatibles ; l'interceptor "gitea" n'existe pas).
  4. ApplicationSet itssolutions-apps — scmProvider gitea, cloneProtocol: https, filtre .*-config$ → chaque repo <app>-config devient une Application Argo.
✓ Boucle validée de bout en bout

push demo-app → webhook → build → Harbor → bump demo-app-config → Argo → https://demo-app.apps.itssolutions.me

Phase 4

Portail développeur · Backstage déployé

Un portail où un développeur crée une application en un clic.

⚠ La leçon fondatrice

L'image ghcr.io/backstage/backstage est une démo, pas un produit. Elle a causé 51 redémarrages MigrationLocked sur ses plugins signals et mcp-actions. La méthode supportée : générer SA propre app et builder SA propre image. Et create-app inclut aussi ces plugins par défaut — les retirer d'index.ts est le fix décisif.

  1. CloudNativePG + Cluster backstage-db (PostgreSQL 17). Le rôle backstage exige CREATEDB (Backstage crée une base par plugin, 12 au total).
  2. backstage-app généré sur le poste (Node via nvm, jamais le nodejs dnf qui crashe sur RHEL) :
    • npx @backstage/create-app (interactif — jamais en nohup)
    • ajout du module plugin-scaffolder-backend-module-gitea
    • retrait de signals, mcp-actions, kubernetes de packages/backend/src/index.ts
  3. Pipeline dédié build-backstage — image node:22-bookworm (bug undici/node-gyp sous node 20), toolchain python3 g++ build-essential, computeResources (le champ resources est rejeté par le webhook Tekton v1), timeout 2h, lancé par kubectl create (hors path Argo).
  4. Application backstage — image Harbor taggée SHA, 3 probes toutes sur le endpoint readiness (Backstage ne retente jamais l'init de ses plugins), strategy Recreate + ignoreDifferences: /spec/strategy (au niveau spec) + RespectIgnoreDifferences=true.

Le golden path — l'aboutissement

Template new-microservice : un clic « Create » → nom → le scaffolder crée 2 repos Gitea → webhook → build → ApplicationSet → déploiement.

# validé avec hello-idp — une app en prod, née d'un clic
curl https://hello-idp.apps.itssolutions.me
<h1>hello-idp - IDP itssolutions</h1>
Gotcha connu

Le tag initial du skeleton provoque un ImagePullBackOff transitoire (~3 min) jusqu'au bump du pipeline. Fix durable : que le pipeline bumpe le values.yaml dès le premier build.

Phase 5

Observabilité & policies en finition

Ne plus jamais diagnostiquer à l'aveugle.

Composants

  • kube-prometheus-stack — Prometheus + Alertmanager + Grafana
  • Loki + Promtail — agrégation des logs (datasource Grafana)
  • Kyverno — policy engine (policies en mode Audit)
  • tekton-pruner — ménage auto des PipelineRuns/PVC

Alertes sur-mesure (chacune = un incident vécu)

LonghornVolumeDegraded, LonghornNodeStorageFull, VaultSealed, PodCrashLooping, DeploymentStuckRollout, ImagePullBackOff, KubeNodeNotReady, NodeMemoryPressure, CertificateExpiringSoon.

Le grand nettoyage révélé par le monitoring

Le déploiement a mis au jour six mois d'archéologie invisibles : un ancien kube-prom-stack (194 j) avec des node-exporters à 26 000+ redémarrages, des KSM/ promtail zombies, un squelette rook-ceph, un gitlab-agent résiduel. Nettoyage → crash-loopers réduits de ~10 à 4.

⚠ Piège Kyverno — verrouillage total du cluster

Le webhook validate.kyverno.svc-fail en failurePolicy: Fail : quand Kyverno tombe, plus aucune création de ressource n'est possible dans tout le cluster. Nos policies étant en Audit, ce mode Fail ne protège rien mais paralyse tout. Fix : webhooksFailurePolicy: Ignore. Débocage d'urgence : supprimer les webhookconfigurations (Kyverno les régénère).

Phase 6

Résilience & SSO en cours

6a — Backups (Velero + MinIO) reporté

Bundle prêt (MinIO backend S3, Velero en file-system backup compatible Longhorn, 3 schedules). Reporté au profit du SSO — reste la dette n°1 (Gitea non sauvegardé).

6b — SSO plateforme (Dex + Gitea) en cours

Choix : Dex, pas Keycloak. Dex est un traducteur OIDC léger (~50 Mo, stateless) qui délègue l'identité à Gitea (connector natif). Un compte Gitea = le login unique de Backstage, Argo CD, Grafana et Harbor. Chaque service garde son admin local en break-glass. Migration Keycloak possible plus tard (indolore, OIDC) si besoin de MFA/LDAP.

Diagnostic

La saga du disque le fil rouge

Le fil rouge du projet, résolu grâce au monitoring de la Phase 5 — et l'histoire la plus instructive de tout le déploiement.

Les symptômes (des semaines d'incidents sans lien apparent)

  • Volumes Longhorn en degraded permanent, jamais reconstruits
  • Bases de données qui redémarrent seules ; Gitea à 12 s par requête SQL
  • kube-state-metrics en CrashLoop (/livez got 0)
  • Backstage / Loki qui ne deviennent jamais ready ; le master qui crashe pendant un build

La chaîne causale

Disque master lent ──▶ etcd "request timed out" ──▶ API server rate des réponses ──▶ Longhorn ne réconcilie plus ──▶ volumes degraded, attach/detach interminables ──▶ DB restarts, Gitea lent, Loki jamais ready

Le dashboard Loki a montré les logs Longhorn : etcdserver: request timed out en boucle — 546 000 logs en 30 minutes.

Les mesures (iostat sur le master)

MétriqueMesuréSain
f_await (latence fsync)97-340 ms< 10-25 ms
disque %util84-100 %< 70 %
IOPS à saturation~25 (HDD-class)—
CPU steal0.3-0.8 %OK (pas de surallocation)
CPU idle~76 %12 cœurs qui attendent le disque

Le traitement

  1. fait Taint NoSchedule du master vérifié.
  2. fait Conversion du bus disque master IDE → VirtIO SCSI (dracut virtio, snapshot, reattach scsi0, boot order).
  3. constat La conversion SCSI n'a pas suffi — f_await reste 150-340 ms. Le bus n'était pas la seule cause : le disque physique (qcow2 sur le stockage local de Proxmox) est le vrai goulot, probablement un HDD.
  4. à faire Vérifier sur l'HÔTE Proxmox : 
    lsblk -d -o NAME,ROTA,SIZE,MODEL   # ROTA=1 = HDD → cause de fond
    Fix : SSD/NVMe dédié au disque master. Atténuation en attendant : --heartbeat-interval=500 --election-timeout=5000 dans les extraArgs d'etcd.

Synthèse

Leçons d'architecture

  1. apply vs create : objets à état nommé → Argo (apply) ; objets à generateName (PipelineRun) → kubectl create, hors path Argo (runbooks/).
  2. RWO + RollingUpdate = deadlock : un volume ReadWriteOnce ne peut être tenu par deux pods → strategy Recreate pour tout workload monobloc sur PVC RWO.
  3. ignoreDifferences ne protège qu'en lecture — ajouter RespectIgnoreDifferences=true pour que le sync n'écrase pas un patch manuel.
  4. Simples quotes pour tout secret contenant $.
  5. Nuage gris Cloudflare pour des IP privées.
  6. Les sous-charts Bitnami sont morts → PostgreSQL via CloudNativePG.
  7. Après un helm uninstall, vérifier les objets cluster-scoped orphelins : CRDs et surtout webhookconfigurations — un webhook qui pointe dans le vide empoisonne l'API.
  8. Une image démo upstream n'est pas un produit (Backstage).
  9. Node 22 pour les builds Backstage (bug undici sous node 20).
  10. Snapshots Proxmox AVANT chaque opération à risque.
  11. etcd sur disque lent = cluster ingérable — un SSD/NVMe pour le master est un prérequis, pas un luxe. Le monitoring transforme un incident mystérieux en un chiffre (f_await).
  12. Kyverno failurePolicy: Fail = risque de verrouillage total ; en Audit, préférer Ignore.
  13. Le monitoring paie sa dette dès le déploiement : il révèle stacks fantômes et instabilité de l'API invisibles autrement.
